# Module 3 — Parallel Execution ด้วย Swarm Pattern

> **เวลา:** ~60 นาที (สอน 25 + Workshop 1 35) | **ผลลัพธ์ที่คาดหวัง:** ผู้เรียนสั่งงาน Subagent หลายตัวขนานกันจาก Prompt เดียว และได้รายงานรวมกลับมาที่ Leader

## 1. Subagent ทำงานอย่างไร

เมื่อ Leader (บทสนทนาหลักของ Claude Code) ได้รับโจทย์ มันสามารถ **dispatch Subagent** — สำเนาที่มี:

- **Context แยก** — ไม่เห็นบทสนทนาหลัก (ได้เฉพาะโจทย์ที่ Leader เขียนส่งให้)
- **Tools ของตัวเอง** — เช่น Explore อ่านได้อย่างเดียว
- **ขอบเขตชัดเจน** — ทำจบแล้ว "สรุปผล" กลับมาเท่านั้น

ประโยชน์ที่แท้จริง: งานที่ output ยาวมาก (สแกน 20 ไฟล์, ค้น 50 หน้าเว็บ) จะไม่ท่วม context ของบทสนทนาหลัก — Subagent อ่านเองแล้วสรุปสั้น ๆ มาให้ แต่จำทางกลับกันด้วย: **Subagent ไม่ได้ทำให้ถูกลง — มันทำให้ session หลักเบาลง** (ทุก dispatch มี overhead: ข้อความมอบงาน + system prompt ของ agent + รายงานสรุป) — งานเล็กที่ผ่านหมด ทำใน session หลักถูกกว่า

**สิ่งที่ Subagent ได้รับตอนเริ่มงาน** (ตามเอกสารทางการ): system prompt ของตัวเอง (จาก definition หรือ built-in — **ไม่ใช่** system prompt เต็มของ Claude Code) · ข้อความมอบงานจาก Leader · CLAUDE.md ทุกระดับ (ยกเว้น Explore/Plan และ agent ที่ตั้ง `omitClaudeMd: true`) · git status ณ ตอนเริ่ม (Explore/Plan ข้ามเช่นกัน) · เนื้อหา skill ที่ระบุใน `skills` **สิ่งที่ไม่ได้รับ:** ประวัติสนทนา, ไฟล์ที่ Claude อ่านไปแล้ว, skill ที่เคยเรียกในบทสนทนา, output style และ auto memory ของ session หลัก — นี่คือเหตุผลที่ข้อความมอบงาน (หัวข้อ 2) ต้องครบด้วยตัวเองทั้งหมด

## 2. Leader-first Interaction — วิธีสั่งที่ถูก

หลักการ: **ส่ง "โจทย์ระดับสูง" ให้ Leader ก่อน แล้วให้ Leader เป็นคนแตกงาน** — อย่าสั่งละเอียดเอง เพราะ Leader รู้จักเครื่องมือและจัดการ dispatch ให้

Anatomy ของ prompt สั่ง Swarm ที่ดี:

```text
[1. บริบท]     สิ่งที่ Leader ควรรู้ก่อน (แอปอะไร, อยู่ไหน)
[2. เป้าหมาย]   ผลลัพธ์สุดท้ายหน้าตาเป็นอย่างไร
[3. การแตกงาน]  ให้แบ่งเป็นกี่ส่วน แต่ละส่วนทำอะไร (หรือให้ Leader เสนอ)
[4. รูปแบบผล]   รายงานรวมยาวเท่าไร โครงหน้าตาอย่างไร
[5. ขอบเขต]     ห้ามทำอะไร (แก้ไขไฟล์, รันคำสั่งที่เสี่ยง)
```

**ข้อความมอบงาน 5 ส่วน — อีกหนึ่งระดับที่ต่ำกว่านั้น:** anatomy ข้างบนใช้ตอนสั่ง Leader ครั้งเดียว แต่งานที่ Leader แตกให้ Subagent แต่ละตัวก็ต้องเขียนให้ครบ — เพราะไม่มี Subagent ตัวไหน (ยกเว้น fork — หัวข้อ 6) เห็นประวัติสนทนาของคุณเลย สิ่งที่ "ทุกงานต้องรู้" ให้อยู่ใน CLAUDE.md (Module 4 หัวข้อ 1) ส่วนที่เหลือซึ่งเฉพาะงานนี้ ต้องอยู่ในข้อความมอบงานครบ 5 ส่วน:

```text
[1. บริบท]        งานนี้คืออะไร อยู่จุดไหนของโจทย์ใหญ่
[2. ไฟล์]          อ่าน/แก้ไฟล์อะไรได้
[3. ผลที่ต้องส่ง]   ต้องส่งอะไรกลับ รูปแบบอย่างไร
[4. ข้อห้าม]        ห้ามแตะอะไร
[5. ทีม]           ใครทำส่วนไหนอยู่ — กันทำซ้ำ/กันทับงานกัน
```

## 3. Prompt ตัวอย่างหลักของ Workshop 1 ✅ tested (runs/module-03/)

```text
This is a small Node.js demo shop project. Dispatch 3 parallel Explore
subagents to investigate it:
1. Map the project structure and how the server starts.
2. List every HTTP endpoint and what each one does.
3. Flag suspicious code patterns worth a security/quality review.
Return ONE consolidated report under 300 words, grouped by the 3 areas.
Do not modify any files.
```

อ่านทีละส่วน:

| ส่วน | ทำหน้าที่ |
|---|---|
| `Dispatch 3 parallel Explore subagents` | บอก Leader ให้ใช้ tool สร้าง Subagent ชนิดอ่านอย่างเดียว 3 ตัวพร้อมกัน |
| เลข 1–3 (สาม task) | งานที่ "ไม่ขึ้นต่อกัน" — จึงขนานได้ปลอดภัย |
| `Return ONE consolidated report under 300 words` | บังคับ Leader สรุปรวม ไม่ตอกย้ำรายงานดิบยาว ๆ |
| `Do not modify any files` | ขอบเขต — ป้องกัน Agent แก้โค้ดเกินหน้าที่ |

### เวอร์ชันภาษาไทย (✅ tested — runs/module-03/run-008)

```text
นี่คือโปรเจกต์ร้านค้าตัวอย่างที่เขียนด้วย Node.js จง dispatch Explore subagent แบบขนานกัน 3 ตัวเพื่อสำรวจโปรเจกต์นี้:
1. สำรวจโครงสร้างโปรเจกต์และวิธีที่ server เริ่มทำงาน
2. รายการ HTTP endpoint ทั้งหมดพร้อมระบุว่าแต่ละตัวทำอะไร
3. ชี้ code pattern ที่น่าสงสัยซึ่งควรได้รับการ review เรื่องความปลอดภัยหรือคุณภาพ
ส่งรายงานรวมเป็นชุดเดียวไม่เกิน 300 คำ แบ่งตาม 3 หมวดข้างต้น ห้ามแก้ไขไฟล์ใด ๆ
```

ผลจริงเทียบกับเวอร์ชัน EN (run-002): dispatch ขนานเหมือนกันทุกประการ แต่**รายงานออกเป็นภาษาไทยทั้งชุด** — สิ่งที่ควรเป็นภาษาเทคนิค (`server.js:86`, ชื่อ endpoint, HTTP method) ยังถูกพิมพ์ถูกต้อง และ Agent จัด severity HIGH/MEDIUM/LOW ให้เอง

## 4. วิธีรัน — 2 โหมด

**TUI แบบโต้ตอบ (ในชั้นเรียน):**

```bash
cd labs-sandbox/demo-shop
claude
```

แล้ววาง prompt ข้างบน — สังเกตหน้าจอ: Leader จะเรียก Task tool แล้วแสดง Subagent ทำงานพร้อมกัน

**Headless (สำหรับทดสอบ/ระบบอัตโนมัติ):**

```bash
claude -p "<prompt>" --allowedTools "Task" --max-turns 20
```

- `--allowedTools "Task"` — อนุญาตการ dispatch Subagent ล่วงหน้า (headless ไม่มีคนกดอนุมัติ)
- `--max-turns 20` — เพดานรอบการทำงาน กันวนไม่สิ้นสุด

## 5. ผลที่คาดหวัง (จากการรันจริง)

Leader dispatch 3 Subagents → รายงานรวมแบ่ง 3 หมวด: โครงสร้างโปรเจกต์ / endpoints ทั้งหมด (ระบุ GET /api/products, GET /api/products/:id, POST /api/cart/total, GET /api/admin/stats) / จุดน่าสงสัย (เช่น JSON.parse ไม่มี try-catch, hardcoded token) — transcript จริงดูได้ที่ [runs/module-03/](../../runs/module-03/)

## 6. สัญญาณว่าแบ่งผิด — วินิจฉัยจากอาการแล้วแก้

การแตกงานไม่ใช่ศาสตร์แม่นยำ — dispatch ไปแล้วให้สังเกตอาการ เจอสักข้อแปลว่าแบ่งผิดจุด:

| สัญญาณ | หมายความว่า | แก้อย่างไร |
|---|---|---|
| Agent ส่งข้อความหากันบ่อยมาก | สองส่วนนี้ผูกกันแน่นเกินกว่าจะแยก | รวมเป็นตัวเดียว หรือเขียนสัญญากลางที่ชัดกว่านี้ |
| ไฟล์ชนกัน | เจ้าของไฟล์ไม่ชัด | แบ่งใหม่ตามไฟล์ หรือให้แต่ละตัวอยู่ใน worktree ของตัวเองแล้ว merge |
| รอกันเป็นทอด | งานเรียงลำดับ ไม่ได้ขนานจริง | ทำในตัวเดียว หรือเรียงเป็นชั้นตามการพึ่งพา |
| ผลไม่ต่อกัน | ไม่มีสัญญาที่จุดเชื่อม | เขียนสัญญากลางก่อนแบ่งงาน |
| Agent ทำงานบนสมมติฐานผิด | ข้อความมอบงานขาดบริบท | เติมบริบทใน task หรือใช้ fork |
| ข้อความสวนกัน — รายงานว่า "ยังไม่ถูกแก้" ทั้งที่แก้แล้ว | หลายตัวแตะเอกสารเดียวกันตอนมันกำลังเปลี่ยน | เอกสารชิ้นเดียวมีเจ้าของคนเดียว แล้วส่งตรวจตอนแก้เสร็จรอบนั้นเท่านั้น |

สองสถานการณ์ที่เล่าให้เห็นภาพ (รูปแบบปัญหาที่พบบ่อยในงานจริง — ไม่ใช่ run ทดสอบของคอร์ส):

- **ข้อความสวนกัน:** ทีมวิจัยส่ง reviewer สองคนไปตรวจ DESIGN.md ระหว่างที่ผู้เขียนกำลังแก้รอบล่าสุดอยู่ ทั้งคู่จึงรายงานว่าสิ่งที่ขอไป "ยังไม่ถูกแก้" — ทีมเสียข้อความไล่กันหลายรอบ บทเรียน: เอกสารชิ้นเดียวที่หลายคนตรวจควรมี**เจ้าของคนเดียว** แล้วส่งตรวจเมื่อแก้เสร็จรอบนั้นเท่านั้น
- **รอกันเป็นทอด:** workflow ย้าย JavaScript → TypeScript ทั้ง 8 ไฟล์พร้อมกัน พังแค่ 2 ไฟล์ — คู่ที่ไฟล์หนึ่ง `require` อีกไฟล์หนึ่ง งานที่ดูเหมือนขนานได้มี**ลำดับซ่อนอยู่** — เช็ค dependency ระหว่างไฟล์ก่อนประกาศว่าขนานได้

สองคำในตารางที่ยังไม่เจอในบทนี้ (อ้างเอกสารทางการ — ยังไม่ได้ทดลองในคอร์ส):

- **fork** — Subagent พิเศษที่ **สืบทอดบทสนทนาทั้งหมดถึงตอนนั้น** (system prompt, tools, ประวัติข้อความ) แทนการเริ่ม context เปล่า — เหมาะกับงานที่ต้องใช้บริบทเดิมเยอะ แต่ tool calls ของมันยังไม่ท่วมบทสนทนาหลัก (เฉพาะผลลัพธ์สุดท้ายที่กลับมา) เรียกด้วย `/subtask` (ตั้งแต่ v2.1.212) หรือให้ Leader เลือกชนิด `fork` เอง · กติกาเบื้องหน้า/เบื้องหลังขึ้นกับ fork mode: TUI (เปิด default) ทุก Subagent รันเบื้องหลัง ส่วน `-p` Claude เลือกเอง ปกติเบื้องหลังเว้นแต่ต้องใช้ผลก่อนทำต่อ (ตามเอกสารทางการ)
- **worktree** — แยก agent ไปทำงานบนสำเนา repo คนละ directory แล้วค่อย merge กลับ — กำหนดที่ frontmatter `isolation: worktree` ได้เลย (ตาราง frontmatter ใน Module 4)

ส่วน "สัญญากลาง" ที่โผล่สองแถวคือหัวข้อจริงจังของ Module 7 (Workshop 4) และ Capstone — ตอนนี้เก็บไว้เป็นสัญชาตญาณก่อน: **ยิ่งจุดเชื่อมระหว่างงานชัด ยิ่งแบ่งขนานได้มั่นใจ**

## 7. Checklist ก่อนแบ่งงาน

หลักคิดหนึ่งเดียว: **แบ่งตาม context ไม่ใช่ตามประเภทงาน** — ให้แต่ละตัวถือส่วนหนึ่ง "ครบทุกขั้น" แล้วส่งต่อกันเฉพาะจุดเชื่อมที่เขียนเป็นสัญญาได้ ไม่ใช่ตัดหน้าที่เป็นชิ้น ๆ แล้วคอยส่งของข้ามตัวทุกขั้นตอน

สามวิธีแบ่งที่ได้ผลจากการใช้งานจริง:

1. **ตามเจ้าของไฟล์** — ตกลงก่อนว่าตัวไหนแตะไฟล์ไหนได้ ไม่มีสองตัวแตะไฟล์เดียวกัน
2. **ตาม layer ที่มีสัญญา API** — เช่น frontend/backend ทำขนานกันบนสัญญา endpoint เดียวกัน (โครงเดียวกับ Capstone)
3. **ตามสมมติฐาน** — งานสำรวจที่มีหลายทางเป็นไปได้ ให้แต่ละตัวตรวจสมมติฐานของตัวเองแล้วเทียบผล

รัน checklist นี้ก่อน dispatch ทุกครั้ง:

- [ ] แต่ละส่วนมีเจ้าของคนเดียว และไฟล์ไม่ทับกัน
- [ ] ไฟล์ร่วม (`package.json`, `app.ts`, schema) มีคนรับผิดชอบชัดเจน
- [ ] จุดเชื่อมระหว่างส่วนมีสัญญาที่เขียนไว้ก่อนเริ่ม
- [ ] ข้อความมอบงานครบห้าส่วน (หัวข้อ 2)
- [ ] สิ่งที่ทุกงานต้องรู้อยู่ใน CLAUDE.md แล้ว (Module 4 หัวข้อ 1) — ไม่หลุดมาเป็น task ซ้ำ ๆ
- [ ] ส่วนไหนต้องรอส่วนอื่น จัดเป็นลำดับไว้แล้ว — ไม่หวังว่าจะขนานได้

## 8. กับดักที่พบบ่อย

- สั่ง "หาทุกอย่าง" โดยไม่จำกัดความยาวรายงาน → ได้ผลลัพธ์ท่วม context
- แตกงานที่ "ขึ้นต่อกัน" ให้ขนาน → ผลขัดแย้งกัน (ตัวหนึ่งสมมติ A อีกตัวสมมติ B)
- ลืม `Do not modify` ในงานสำรวจ → Agent แก้โค้ดไปด้วยโดยไม่ได้ขอ
