# Module 1 — สถาปัตยกรรม AI Agent และแนวโน้มปัจจุบัน

> **เวลา:** ~45 นาที (บรรยาย + สาธิต) | **ผลลัพธ์ที่คาดหวัง:** ผู้เรียนเลือกรูปแบบ Multi-Agent (Swarm / Sequential / Orchestration) ให้ตรงกับลักษณะงานได้ และประเมินต้นทุน Token ได้

## 1. จาก Chatbot สู่ Agent — ต่างกันตรงไหน

**Chatbot** ตอบคำถามแล้วจบ — ไม่มีอะไรเปลี่ยนในโลกจริง

**Agent** ทำงานให้สำเร็จด้วยวงจร (agentic loop):

```text
รับโจทย์ → วางแผน → เลือกเครื่องมือ (Tool Calling) → ลงมือทำ → ตรวจผล → แก้/ทำต่อ → ส่งมอบ
```

กลไกที่ทำให้วงจรนี้เป็นไปได้คือ **Tool Calling**:

1. โมเดลได้รับ "รายการเครื่องมือ" พร้อมคำอธิบายหน้าที่ของแต่ละตัว
2. เมื่อโจทย์ต้องการ โมเดลจะตอบเป็นคำสั่งเรียกเครื่องมือ (tool use) แทนข้อความธรรมดา
3. รันไทม์ (Claude Code) รันเครื่องมือนั้นจริง แล้วส่งผลลัพธ์กลับเข้า context
4. โมเดลอ่านผล ตัดสินใจขั้นถัดไป — วนซ้ำจนงานเสร็จ

> ประเด็นสอน: พลังของ Agent ไม่ได้มาจาก "โมเดลฉลาดขึ้น" แต่มาจาก **การให้โมเดลมีมือและตา** (tools + feedback loop)

## 2. แผนที่ Multi-Agent ใน Claude Code (ปี 2026)

| รูปแบบ | คืออะไร | เหมาะกับ | ต้นทุน |
|---|---|---|---|
| **Subagent** | สำเนาของ Claude ที่มี context/system prompt/tools แยกของตัวเอง ทำงานเสร็จแล้วสรุปผลส่งกลับผู้เรียก | งานโฟกัสที่ output ยาวมาก (สแกนโค้ด, ค้นคว้า) ไม่อยากให้บดบังบทสนทนาหลัก | ต่ำสุด |
| **Agent Teams** (experimental) | หลาย instance ของ Claude Code คุยกันเองได้ มี Task List ร่วม มี Team Lead คนหนึ่ง | งานซับซ้อนที่ต้องถกเถียง/ประสานข้ามสายงาน | สูง |
| **Background Agents** | Subagent ที่รันอยู่เบื้องหลัง ไม่บล็อกการสนทนา | รัน test suite / build ยาว ๆ ระหว่างทำงานอื่น | ปานกลาง |

**Built-in Subagents ที่ต้องรู้จักก่อนสร้างของตัวเอง:**

- `Explore` — ตัวอ่านอย่างเดียว (อ่าน/ค้น/สรุป ห้ามแก้ไข) เหมาะกับงานสำรวจ
- `Plan` — ใช้ใน Plan Mode เพื่อค้นคว้าก่อนเสนอแผน
- `General-purpose` — ทำได้ทุกอย่าง รวมแก้ไขไฟล์

## 3. Orchestrator–Worker — แพทเทิร์นหลักของทีม Agent

ทีมวิจัยของ Anthropic เปิดเผยสถาปัตยกรรมที่ใช้จริง ("How we built our multi-agent research system"):

```text
                 ┌──> Subagent A (ค้นแหล่ง X) ──┐
Leader Agent ────┼──> Subagent B (ค้นแหล่ง Y) ──┼──> Leader สังเคราะห์ → คำตอบ
(วางแผน/แจกงาน)  └──> Subagent C (ตรวจผล) ─────┘
```

- **Leader** วิเคราะห์โจทย์ → วางแผน → แตกงานเป็น task ที่ระบุชัด: วัตถุประสงค์ / รูปแบบผลลัพธ์ / เครื่องมือที่ควรใช้ / ขอบเขต
- **Workers** ทำงานขนานกัน แต่ละตัวมี context ของตัวเอง
- Leader รวมผล แล้วปล่อยรอบเพิ่มถ้ายังขาดข้อมูล

**ตัวเลขที่ควรจำ** (จากรายงาน Anthropic):

- Multi-agent ทำงานวิจัยกว้าง ๆ ได้ดีกว่า single-agent **+90.2%**
- แต่ใช้ Token **~15 เท่า** ของการแชทธรรมดา
- Token อธิบายผลลัพธ์ได้ ~80% — คุม Token = คุมคุณภาพ/งบ
- เหมาะกับงานที่ **ขนานได้และอ่านหนัก** (research, review, สแกน) — ไม่เหมาะกับงานที่ตัวต่อตัวต้องแชร์ context แน่น (โค้ดชิ้นเดียวกันแก้ไปแก้มา)

## 4. ตัดสินใจ: Swarm (ขนาน) หรือ Sequential (ต่อคิว)

คำถามตัดสินมีข้อเดียว: **"งานลูกต้องรู้ผลลัพธ์ของงานพี่ไหม?"**

| สถานการณ์ | เลือก | เหตุผล |
|---|---|---|
| สำรวจ 5 โฟลเดอร์ไม่เกี่ยวกัน | Swarm ขนาน | เร็วขึ้น ~90% ผลไม่ขึ้นต่อกัน |
| ออกแบบ → สร้าง → ตรวจ | Sequential | ด่านหลังต้องใช้ artifact ของด่านหน้า |
| Frontend + Backend บน API spec เดียว | Swarm (หลังมีสัญญากลาง) | สัญญาชัด = ขนานได้ปลอดภัย |
| แก้ bug เดียวที่ไล่ยาก | อย่าใช้ทีม | Multi-agent บวมโดยไม่จำเป็น |

> กลาะเตือนจากชุมชน: Subagent ที่ขนานกันโดยไม่มี "สัญญากลาง" (spec/contract) จะตัดสินใจขัดแย้งกันเอง — เช่น ใช้ชื่อ API คนละแบบ เพราะไม่เคยเห็นงานกัน
