# Module 3 — Swarm / Parallel exploration

> ⏱ ~60 นาที · 🎯 สั่งครั้งเดียวให้ leader ปล่อย Explore สามตัวแล้วรวมรายงานโดยไม่แก้ไฟล์ · One prompt dispatches three read-only explorers and returns a single short report.

## Key idea / แนวคิดหลัก — เล่าเป็นเรื่อง

วันจริงของแอป Sales Insight จะมีคำถามสามกลุ่มที่ตอบไม่จบ: โครงสร้างโปรเจกต์เดินอย่างไร ข้อมูลใน CSV สะอาดแค่ไหน และโค้ดส่วนไหนมีพฤติกรรมเสี่ยง ถ้าให้บทสนทนาหลักอ่านทุกไฟล์เองตามลำดับ คำตอบที่ยาวจะท่วมบทสนทนาทีละนิด จนถึงจุดหนึ่ง Claude เริ่มลืมสิ่งที่คุยกันไปแล้วด้านบน

Swarm คือทางออกของปัญหานี้ — คุณสั่ง leader เพียงครั้งเดียว มันแตกงานเป็นเอเจนต์ย่อยสามตัวที่อ่านคนละส่วนพร้อมกัน แต่ละตัวเปิดไฟล์เองในโลกของตัวเอง แล้วส่งกลับมาแค่บทสรุป สิ่งที่ leader (และคุณ) เห็นจึงเป็นรายงานสามหัวข้อ ไม่ใช่เนื้อไฟล์เต็ม ๆ สิบฉบับ — บทสนทนาหลักจึงเบาพอจะคุยงานต่อได้อีกนาน

ข้อกันพลาดอยู่ที่คำว่า "พร้อมกัน": swarm ใช้ได้เฉพาะก้อนงานที่ไม่ต้องรอผลกัน เราเลือก `Explore` เป็นชนิดสำรวจเพราะมันอ่านอย่างเดียว — อ่านได้เร็วเพราะระบบตัดสิ่งฟุ่มเฟือยออกให้ และอ่านอย่างเดียวจึงแก้ไฟล์ไม่ได้แม้จะอยาก

> EN: One leader prompt, three parallel Explore subagents, no edits, one short merged report.

## Concept / เนื้อหา

ตัวชี้ว่าแบ่งถูกหรือผิดอยู่ที่ขอบเขต ในแล็บนี้เราแตกงานเป็นสามก้อนที่ไม่ง้อกัน:

1. **โครงสร้าง** — `server.js`, `web/`, `mcp/`, `scripts/` และวิธียกเซิร์ฟเวอร์
2. **ข้อมูล** — คอลัมน์ใน `data/README.md` และข้อความ FAIL ที่ quality gate รายงาน
3. **ความเสี่ยง** — ทางที่เซิร์ฟเวอร์อ่าน CSV และทางที่รับ `POST /api/notes`

สามก้อนนี้อ่านไฟล์คนละชุด ไม่มีใครต้องรอคำตอบของอีกตัว จึงวิ่งขนานได้จริง

สัญญาณบอกว่าแบ่งผิด (เจอสักข้อแปลว่าต้องรวมหรือแบ่งใหม่):

| อาการ | ความหมาย |
|---|---|
| เอเจนต์ย่อยส่งข้อความหากันยาว | งานผูกกันเกินกว่าจะแยก |
| ไฟล์ชน | เจ้าของไฟล์ไม่ชัด |
| รอกันเป็นทอด | นี่คืองานต่อคิว ไม่ใช่ swarm |
| สรุปคนละสมมติฐาน | ยังไม่บอกกันว่าข้อมูลต้องเชื่อมกันยังไง |

ก่อนกดส่ง ตรวจสามข้อ: แต่ละก้อนมีเจ้าของคนเดียว, บอกแล้วว่าข้อมูลต้องเชื่อมกันอย่างไร, และใส่ประโยคห้ามแก้ไฟล์แล้ว — สามข้อนี้คือเหตุผลที่ prompt ตัวอย่างด้านล่างยาวแบบที่เห็น

## ลงมือทำตามลำดับ

```bash
claude
```

1. วาง prompt จากหัวข้อถัดไปลงใน TUI — สังเกตหน้าจอ: leader จะเรียก Task tool แล้วแสดงเอเจนต์ย่อยสามตัวทำงานพร้อมกัน
2. รอรายงานรวมที่มีสามหัวข้อ (โครงสร้าง / คุณภาพข้อมูล / จุดเสี่ยง) ยาวไม่เกิน 300 คำ
3. ยืนยันว่าสำรวจไม่ทำลาย:

```bash
git status
```

   ไม่ควรมีไฟล์ของแอปเปลี่ยนจากรอบสำรวจ — ถ้ามี แปลว่าประโยคห้ามแก้หลุดจาก prompt

หมายเหตุ headless: ถ้าต้องรันนอก TUI จริง ๆ คำสั่งคือ `claude -p "<prompt>" --allowedTools "Task" --max-turns 20` จากโฟลเดอร์แอป แต่แล็บในห้องไม่ใช้ทางนี้ — คุณภาพการเรียนรู้อยู่ที่การเห็นเอเจนต์วิ่งสด ๆ

## Prompt pattern — เลือกใช้อย่างใดอย่างหนึ่ง

**เวอร์ชันอังกฤษ (แนะนำ):**

```text
Dispatch 3 parallel Explore subagents on this Sales Insight app.
1) Map the runtime files and how to start the server.
2) Read data/README.md and the failure text from node scripts/quality-gate.js. Do not fix anything.
3) Trace GET /api/summary and POST /api/notes far enough to name the risky behavior.
Do not modify files. Return one report under 300 words with headings: structure, data quality, risks.
```

**เวอร์ชันไทย (ใช้ได้เต็มที่):**

```text
ส่ง Explore subagent 3 ตัวทำพร้อมกันในแอป Sales Insight
1) แผนที่ไฟล์ที่ใช้รัน และวิธียกเซิร์ฟเวอร์
2) อ่าน data/README.md และข้อความ FAIL จาก node scripts/quality-gate.js ห้ามแก้
3) ไล่ GET /api/summary กับ POST /api/notes พอให้ชี้พฤติกรรมที่เสี่ยง
ห้ามแก้ไขไฟล์ ส่งรายงานเดียวไม่เกิน 300 คำ มีหัวข้อ โครงสร้าง, คุณภาพข้อมูล, จุดเสี่ยง
```

> 📚 **ทำไมแนะนำ EN:** ภาษาของ prompt เป็นตัวกำหนดภาษาของรายงาน — คอร์สทดสอบคู่กันไว้แล้ว (EN ได้รายงานอังกฤษ, TH ได้รายงานไทย, คุณภาพการสำรวจเท่ากัน) รายงานฉบับนี้จะถูกอ้างต่อใน Workshop ถัด ๆ ไป ซึ่งของที่ถูกอ้าง (ชื่อ endpoint, `file:line`, หัวข้อ structure / data quality / risks) เป็นอังกฤษทั้งหมด รายงานอังกฤษจึงต่อกันเนียนที่สุด และเวลาห้องเทียบผลท้ายแล็บทุกคนอยู่รูปแบบเดียว ถ้าคุณสะดวกอ่านไทย TH ใช้ได้เต็มสิทธิ์ — ของเทคนิคในรายงาน (ชื่อไฟล์, endpoint, severity) ยังถูกพิมพ์ถูกต้องเสมอ

| ส่วน | หน้าที่ |
|---|---|
| Dispatch 3 parallel Explore | บังคับชนิดและจำนวน |
| เลข 1–3 | ก้อนงานคนละบริบท |
| Do not modify / ห้ามแก้ไข | กันเอเจนต์ลงมือแก้ |
| under 300 words | กันสรุปยาวจน leader อ่านไม่ไหว |

## Common pitfalls / กับดัก

- สั่ง "หาทุกอย่าง" โดยไม่จำกัดคำ — ได้รายงานยาวกลืนบทสนทนาหลัก ซึ่งเป็นปัญหาเดิมที่ swarm ควรแก้ให้
- ลืมประโยคห้ามแก้ไฟล์ — เอเจนต์ย่อยที่เจอบั๊กระหว่างสำรวจมัก "ช่วยแก้" ตามสัญชาตญาณ คุณจะได้ diff ที่ไม่ได้ขอ
- แตกงานที่ต้องใช้ผลกันให้ขนาน — ก้อนที่รอกันจะสรุปคนละสมมติฐาน และคุณต้องเป็นคนกลางเอง
- ใช้ `claude -p` แล้ว Bash ถูกปฏิเสธ — ขั้น quality gate ต้องรันในเทอร์มินัลของคุณเอง แล็บนี้จึงออกแบบให้สำรวจโดยไม่ต้องรันอะไร
- ตั้ง `--max-turns` ต่ำ — เอเจนต์ย่อยยังไม่ทันรวมรายงาน รอบจบแบบไม่มีผล
- เปิดคนละโฟลเดอร์กับแอป — สำรวจผิดที่ตั้งแต่ต้น ตรวจ prompt แรกว่าเปิดจาก ``
